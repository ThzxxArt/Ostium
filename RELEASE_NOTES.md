# Ostium v0.1.2

This is a state-convergence and release-integrity release. It does not add a
new proxy protocol or redesign the UI.

## Highlights

- Quota and expiry enforcement is fail-closed: a failed apply keeps the
  revocation pending instead of letting an over-quota user stay connected.
- The privileged core refuses a server `last-good` configuration generated by
  an older security policy and strips users revoked in the database.
- The control plane reconciles the running core with the database after an
  apply failure, startup, certificate renewal and subscription refresh.
- Backup format v2 includes rule sets and the ACME account key, stores
  certificate/rule-set paths relative to the data directory, verifies
  checksums, and refuses a restore that is missing `master.key` while the
  database contains encrypted data.
- Public UI certificate renewal reloads the TLS listener; an expired
  certificate starts a loopback-only recovery console instead of locking the
  administrator out. Public UI on 8443 now produces subscription URLs with the
  correct port.
- `/auth/status` failures show a retryable error page; an existing installation
  is no longer mistaken for an uninitialised one.
- Rule-set-only rules are reported as unknown (not "match all"), and Python-only
  regex syntax is rejected before sing-box sees it.
- Outbound HTTP fetches pin the validated DNS address, closing the
  rebinding window for subscriptions, rule sets and webhooks.
- The release workflow builds all artifacts, creates and verifies a draft
  release, publishes PyPI only after that verification, then promotes GHCR tags
  and makes the draft public. A failure after PyPI keeps the draft for retry and
  is recovered by yanking the PyPI version or shipping a patch.

## Security and upgrade notes

- Back up the database, configuration, certificates, rule sets and
  `master.key` before upgrading.
- `0.1.1 -> 0.1.2` is tested by `scripts/upgrade-e2e.sh`; users, credentials,
  subscription tokens, backups and the master key are preserved.
- A backup without `master.key` is rejected when the database contains
  encrypted fields. Restore the original key; do not generate a new one.
- Windows/macOS binaries are unsigned unless the release owner supplies signing
  certificates. Check `docs/release-status.md` for the current status.

## Verified

- Local backend, frontend, real-core integration, backup portability, upgrade
  and release-ordering tests.
- Exact command output and counts are recorded in `docs/release-status.md` and
  the release checklist for this tag.

## Not verified / accepted blockers

The following were not executed in the development workspace and are not
claimed as verified: Windows 11 runtime, macOS 14 runtime, Debian/RHEL real
machines, Nginx, Docker runtime, real ACME against a public domain, real TUN,
72-hour soak, performance measurements and platform code signing. See
`docs/release-status.md` for the maintained list.

## Signing and artifacts

Artifacts are published with SHA-256 checksums, a core manifest and GitHub build
provenance attestations. Platform signing is listed separately; do not describe
an unsigned asset as signed.

## Rollback

Keep the previous virtualenv and a database snapshot. Restore the snapshot and
the previous package if the upgrade fails. The backup restore path keeps a
staged backup for retry and restores the previous database on error.
