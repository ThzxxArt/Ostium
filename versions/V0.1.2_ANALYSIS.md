## 2. 项目现状

### 2.1 产品与架构

Ostium 是双角色私人 VPN / 通用代理控制台：

- 同一个 Python 包、同一个 Vue 3 SPA、同一个 CLI；
- 服务端/客户端共用 `ostium.service`（控制面）与 `ostium-core.service`（特权核心）；
- 数据面固定 `sing-box 1.14.4-ostium.1`（`with_v2ray_api`）；
- PyPI 分发名 `ostium-ctl`，CLI/导入名 `ostium`。

服务端 apply 链路：

```text
DB -> EngineManager 生成配置 -> core API /v1/apply
   -> 角色/端口/路径白名单 -> sing-box check
   -> 原子写 last-good -> 重启子进程 -> 存活检查
```

统计链路：

```text
每 5 秒 V2Ray gRPC -> 每 60 秒落库 -> 每 30 秒执行配额/到期
```

### 2.2 已交付能力

- 服务端：Reality、Hysteria2、Trojan、SS2022；多用户/配额/到期/轮换；四种订阅格式 + 二维码；ACME HTTP-01/手动/自签；按 inbound 证书；V2Ray 每用户流量；备份/恢复；审计/告警/诊断；Public UI。
- 客户端：混合代理、系统代理、TUN、智能/全局/直连/自定义分流、FakeIP/DoH、多 Profile、URLTest、Allow LAN。
- 交付：wheel/sdist、5 个核心归档、DEB/AppImage amd64+arm64、macOS arm64 DMG、Windows x64 setup、Docker/GHCR、SBOM、23 个 Release 资产、attestation。

## 3. 关键发现

### 3.1 状态收敛：DB 成功不代表 core 成功

#### P0-01 配额/到期禁用失败被吞，用户继续可用

- `src/ostium/services/stats.py:377-389`：`_disable()` 只有在 `on_quota` 抛异常时才返回 `False`。
- `src/ostium/api/app.py:95-102`：生产 `on_quota` 捕获所有异常、只写日志、不 re-raise。
- `src/ostium/services/stats.py:331-332`：一旦用户 `enabled=False`，下一轮 `enforce_quotas()` 直接 `continue`，不再重试。
- 结果：DB 已写禁用，core 的 last-good 仍允许该用户；重启 core 也直接启动旧 last-good。
- 与 `CHANGELOG.md:40` 的“失败会重试”声明不符。

#### P0-02 升级后旧 last-good 不会自动获得新安全策略

- `src/ostium/engine/singbox/supervisor.py:79-108`：core 启动只校验并启动 last-good，不判断配置由哪个版本生成。
- `src/ostium/api/app.py:124-157`：控制面启动只 `ensure_inbounds`，不主动 apply。
- 0.1.0 的 last-good 只有旧版 metadata/loopback/link-local/ULA 阻断，没有 0.1.1 新增的 RFC1918/CGNAT/多段 metadata 阻断。
- 升级后 core 先跑旧配置，直到管理员下次改用户/线路/证书/设置触发 apply。
- `last-good.meta` 只存 `allow_lan`（`supervisor.py:443-452`），没有 generator/policy/config revision，无法识别陈旧配置。

#### P1-01 FastAPI yield 依赖在响应发送后才 commit

- `src/ostium/api/deps.py:74-83`：`get_session()` 在 `yield` 后 commit。
- 当前 FastAPI 依赖清理发生在响应发送之后。
- 大量变更端点没有显式 commit：密码修改、logout、TOTP、撤销 API token、删除用户、settings/inbounds/rules/profiles/system 的审计写入。
- commit 失败（磁盘满、WAL 锁超时）时客户端可能已收到 200，密码/撤销/删除实际回滚。
- `routes_users` 等先 apply core 再等 teardown commit，可能出现“core 已删用户、DB 仍有用户”或反向不一致。

#### P1-02 core apply 无全局串行化、超时不匹配、无服务端 watchdog

- 控制面没有 apply 串行化；supervisor 的内部锁只保护子进程。
- 两个请求可能基于不同 DB 快照构建配置，最后到达 core 的可能是旧快照。
- `CoreClient` 超时 5 秒（`engine/core_api.py:22`），而 `sing-box check` 允许 30 秒（`supervisor.py:277`）。
- 大配置/并发 apply 时 API 先报 `core_unreachable`，core 实际仍在应用。
- 服务端没有 core watchdog（客户端有 `_core_watchdog`）。
- 多个端点把 `core_unavailable/core_unreachable/engine_unavailable` 变成 200 + warning，没有 dirty flag/retry。

#### P1-03 过期/超额用户只在统计 tick 中被移除

- `_server_spec()` 只筛选 `ProxyUser.enabled`（`manager.py:121-135`），不检查 `expires_at`/`quota_bytes`。
- 真正禁用依赖 `enforce_quotas()`（`stats.py:289-365`）。
- V2Ray stats 不可用时只写一条日志（`stats.py:121-136`），到期用户仍会被写进 core 配置并继续连接。
- 管理员把 `expires_at` 改成过去后，下一次 apply 仍包含该用户，最多等 30 秒 tick；stats 起不来则永久保留。

#### P1-04 统计 reset/flush 竞态与残留

- `flush()` 先读 `user.used_bytes` 再 `+= total`（`stats.py:221-227`），`reset_usage` 直接置 0（`users.py:135-147`），两者无同锁/版本。
- 管理员在刷盘窗口重置，可能被旧值覆盖。
- 月度重置写入 `_epoch_pending` 后若用户在 flush 前被删，`StatsEpoch` FK 插入失败，`_epoch_pending/_pending` 因 commit 失败不清空，之后每次 flush 重复失败。
- `reset_usage` 不清 `_pending`，重置后下一次 flush 会把最多 60 秒旧流量加回。
- `_last/_usage/_alerted/_epochs` 保留已删除用户。

### 3.2 数据生命周期：备份不是可迁移备份

#### P0-03 备份缺规则集、路径不可移植、master.key 缺失静默新建

- `services/backup.py:81-97`：只打包 `ostium.db/master.key/config.toml/certs`，**不含 `rulesets/`**。
- 证书路径、规则集路径以绝对路径入库（`certificates.py:246-249`、`rules.py:257`）。
- 恢复只把文件复制到新的 `certs_dir`（`backup.py:258-272`），不重写 DB 中的 `cert_path/key_path` 与 `rule_sets.path`。
- 换数据目录/用户、Linux↔Windows 迁移后证书和规则集全部不可用；core 的 `allowed_paths` 还会拒绝旧路径。
- `load_or_create_master_key()` 在文件缺失时直接生成新 key（`util/security.py:49-64`）。
- 恢复不含 `master.key` 的备份后，用户密码/TOTP/订阅 token/inbound 参数全部不可解密，但系统不报“密钥不匹配”，而是新建密钥继续写新数据，形成新旧密文混存。
- `restore_backup` 只在归档有 key 时覆盖，不校验配套关系。
- 备份/恢复整文件读入内存（`backup.py:156-166`），2 GiB 备份会打爆控制面；`stage_restore` 读一遍并解密两次（`backup.py:363-379`）。
- `stage_restore` 只校验 manifest，不校验 SQLite（`backup.py:380-403`），坏备份会在下次启动才暴露。
- CLI `backup restore` 不检查服务是否运行（`backup.py:208-210`；`cli/main.py:1706-1723`），会删 WAL/覆盖主库。
- 恢复不清理 `last-good*`/`core-state.json`：同机恢复后 core 可能直接启动恢复前旧配置，暴露已删除用户/旧端口。

#### P1-05 迁移缺少快照、文件锁和真实旧库测试

- `migrate_database()` 直接 `command.upgrade`（`db/session.py:127-137`），没有迁移前 SQLite 快照、失败回滚、文件锁。
- 两个实例同时启动可能并发 Alembic。
- `_has_tables` 只检查 `admin_users`（`db/session.py:93-103`），半初始化/无 `alembic_version` 的库会跑 initial migration 并因表已存在失败。
- `test_existing_010_database_upgrades_in_place` 只是对当前 `create_all` 并 stamped 的库再跑一次迁移（`tests/unit/test_schema_migrations.py:44-57`），没有真实 0.1.0 schema。
- `SCHEMA_HEAD` 是手写常量，没有与 Alembic head 一致性测试。

### 3.3 证书、Public UI 与订阅

#### P0-04 Public UI 证书生命周期会把管理员锁在门外

- `serve` 启动时把证书读入 uvicorn SSLContext（`cli/main.py:431-449`）。
- `_cert_renewal()` 只更新 DB/文件并 apply core（`api/app.py:590-631`），不重载 TLS 监听。
- 续期成功后浏览器仍使用旧证书；旧证书到期后 Public UI 不可访问，即使新证书已在磁盘。
- 反过来，Public UI 启动要求 ready 且未过期证书，否则退出 6（`cli/main.py:389-439`）；自动续期只在应用 lifespan 内运行。**证书过期后重启 → serve 拒绝启动 → 续期永不执行。**
- CLI `cert issue --self-signed` 只创建证书行，不绑定 inbound、不 apply，`auto_renew` 默认 True（`cli/main.py:1765-1778`）。
- 删除 Public UI 正在使用的证书没有保护（`routes_certs.py:331-360`）。
- 续期生成新 generation 后不清旧文件；删除 apply 失败后没有后续清理机制。
- `certificate_is_ready` 不检查文件存在（`certificates.py:332-337`），可绑定丢文件的证书。

##### P0-04 补充：Public UI 8443 的 base URL 缺端口

- `routes_settings.py:342-343`：启用 Public UI 且未设置 `public_base_url` 时写 `https://{domain}`，不含 `settings.port`。
- 默认 Public UI 在 8443，订阅链接指向 443，而 UI/订阅实际在 8443，客户端拉不到订阅。
- 443 变体恰好正确，所以问题只在非 443 Public UI，容易被测试遗漏。
- 前端 Settings 的 Public UI 域名下拉只改本地变量，没有 change/save 处理器；已开启时换域名不会生效。

#### P1-06 订阅节点主机与 base URL 分离

- `server_hostname()` 只读 `server.public_host/domain`，否则返回 `127.0.0.1`（`services/users.py:407-415`）。
- `endpoints_for_user()` 用它填每个 Endpoint 的 `server`。
- `public_base_url()` 可以来自设置，但两者分离；即使设置 `public_base_url=https://vpn.example.com`，Profile 内节点仍是 `127.0.0.1`。
- 首次 Web Setup 的 `domain` 是可选项；跳过之后 `SettingsPatch` 没有 domain 字段；已初始化时 `init` 提前返回。
- 结果：订阅 URL 基地址对了，节点地址仍不可用。

#### P1-07 Nginx 与 Public UI 文档冲突

- `docs/guides/nginx.md:160-161` 建议“在 Settings 开启 Public admin UI”。
- 但 `public_ui=true` 会把 Ostium 监听改为 TLS，并可能把 host 从回环扩到 `0.0.0.0`；Nginx 的 `http://127.0.0.1:8443` 反代立刻 502，同时多出一个公网 TLS 监听。
- `docs/guides/nginx.md:12-19` 仍以“推荐架构”开场，和“Nginx 非主方案”的新教程冲突。
- 正确关系：Nginx 终止 TLS 时保持 `public_ui=false`、`secure_cookies=true`、`trusted_hosts` 包含域名；Public UI 与 Nginx 二选一。

### 3.4 规则、SSRF 与安全边界

#### P1-08 规则测试器忽略 `rule_set`，且正则语义与 sing-box 不一致

- `services/rules.py:123-167` 的 `matches()` 没有 `rule_set` 分支，末尾 `return bool(match)`。
- 只含 `rule_set` 条件的规则对任意目标都匹配，`/rules/test` 显示“全部命中”，block 规则甚至显示阻断所有流量。
- `domain_regex` 用 Python `re` 校验/匹配（`rules.py:51-58,140-142`），Go RE2 不支持 lookahead/backref；保存可通过，`sing-box check` 失败，一条规则即可让整个客户端配置无法应用。
- `re.search` 在事件循环内同步执行，可被 ReDoS 阻塞。
- `domain_suffix` 裸 `endswith`（`rules.py:134-136`）无标签边界，与 Clash/sing-box 语义存在不一致风险。
- 测试器不模拟内置 `ip_is_private`、CN 直连、广告拦截与 `final`，私有 IP/`.cn` 结果与真实路由相反。

#### P1-09 SSRF 校验与真实连接分离（DNS rebinding TOCTOU）

- `validate_remote_url` 先解析并检查全部地址（`netguard.py:128-142`），随后 `fetch_limited` 交给 httpx 重新解析（`netguard.py:194-213`），未把已校验 IP 钉死。
- 攻击者控制域名可先解析公网过检、再解析 127.0.0.1/169.254.169.254。
- 规则集、客户端订阅、Webhook 均受影响。
- `validate_target_host` 完全不做 DNS（`netguard.py:26-47`）；Webhook 保存和 Reality preflight 仅用它预检，preflight 的 `socket.create_connection` 同样可被 rebinding。

#### P1-10 规则集删除/更新可能破坏 last-good

- `delete_rule_set()` 在 `_apply_client()` 返回 `applied:false` 警告时仍 commit 并 unlink（`routes_rules.py:364-380`）。
- 旧 core 仍可能引用该文件，客户端 watchdog reload 旧 last-good 时 `sing-box check` 失败，代理起不来。
- `update_rule_set()` 下载后只算 SHA/写文件，不校验 `binary/source` 格式（`services/rules.py:236-263`）；HTML 错误页会被写入 `.srs`，随后 apply 失败，旧 last-good 指向同一路径，下一次 reload 仍失败。

#### P1-11 Windows UI 数据目录 ACL 可被其他本地用户读取

- `deploy/windows/install.ps1:94` 用 `icacls $DataDir /grant user:M`，没有 `/inheritance:r`。
- `%ProgramData%\Ostium` 默认继承 `Users:(RX)`；`security.py:67-72` 的 `_tighten` 只在 POSIX chmod，Windows 上 `master.key` 不会收紧。
- 本机任意用户可读 UI 的 `ostium.db` + `master.key`，进而破解口令哈希、解密证书私钥/订阅 token。
- 需要 `/inheritance:r` + 仅 SYSTEM/Administrators/安装用户；对 `master.key` 单独 ACL；加“第二用户不可读”测试。

#### P1-12 API token scope 过粗

- API token 只有 `read`/`write` 粗粒度（`deps.py:119-126`）。
- `read` 即可 reveal 订阅 token、下载备份、读用户 UUID、读取明文凭据（`GET /users/{id}/subscription?reveal=true`、`/users/{id}/export`、`/profiles`）。
- 需要细分 scope（如 `subscription:read`、`backup:read`、`user:read`），或对敏感 GET 要求二次确认。

#### P1-13 TOTP 重放、Webhook 密钥明文、脱敏不递归

- TOTP `valid_window=1` 且不记录已用 code（`util/security.py:146-150`），90 秒内可重放。
- `webhook_secret` 明文存 `settings.value_json`（`routes_settings.py:238-240`）。
- `redact_mapping` 不递归 list（`util/redact.py:48-57`）。
- 登录限流知道默认 `admin` 即可持续 DoS；用户名不存在立即返回、密码校验才 Argon2，存在时间侧信道。
- 本地登录 token 单次表在进程内，重启后 5 分钟内可重放。

### 3.5 前端：认证可恢复性与数据完整性

#### P0-05 `/auth/status` 失败被误判为“未初始化”，用户被锁进 setup

- `stores/auth.ts:21-37`：`/auth/status` 失败时只记录 `error`，随后 `ready=true`、`status=null`；`router/index.ts:148-150` 用 `!auth.initialized` 判断并跳 `/setup`。

## 5. 结论

Ostium 的工程基础不差：两服务隔离、字段加密、last-good 回滚、systemd 加固、真实 sing-box 集成、四轮 161 项审查、23 个资产发布，都说明项目已经越过“能跑”的阶段。

当前主要风险不在 happy path，而在**失败后的状态收敛、跨机数据迁移、证书生命周期、发布真实性、平台证据**。这些问题有一个共同特征：本地测试绿、普通路径正常，但在磁盘满、core 不可用、证书过期、升级旧配置、跨机恢复、DNS 重绑定、网络断开时会把用户留在不一致状态。

因此 0.1.2 的正确目标是：

> **让 DB、core、文件、安装器、文档在失败后能收敛到一致状态；让 0.1.1→0.1.2 的升级可自动验证并可回滚；让 tag/PyPI/Release/docs 的发布状态只有一个事实来源。**

不是新增协议，不是 UI 重设计，也不是继续堆平台声明。
