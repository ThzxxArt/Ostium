# Ostium v0.1.11 迭代方案

> 状态：**已批准，待实施；未创建 tag、未修改源码、未发布任何资产**
> 基线：`main` / `329a7fb`（v0.1.10 发布后文档提交）
> 上一版本：`v0.1.10`（已发布，不可变）
> 日期：2026-11-17
> 定位：**可验证性与故障闭环（Verifiability & Failure Containment）**
> 范围：P0 + P1 全部纳入；P2 中属于 0.2.0、外部实机或上游核心改动的项目明确留到后续版本。
> 原则：不新增协议族，不做 UI 重设计，不引入数据库迁移；先把版本、DNS、代理链路、在线语义和安装结果做成可验证、可复现、可回滚。

---

## 0. 一页结论

0.1.10 已经修复服务端 DNS 污染的主根因：部署服务器为 `0.1.10`，`last-good.json` 使用 `8.8.8.8` / `1.1.1.1`，服务器直连 Google 与 Hugging Face 均返回 HTTP 200。继续把 0.1.11 做成“再换一个 DNS”没有意义，当前真正的问题是：

1. **版本不可判定**：`ostium.__version__` 来自运行时 `importlib.metadata`，无法证明当前监听端口的进程、磁盘安装、核心二进制和 Web 构建是同一版本。
2. **安装结果不可判定**：Windows/Linux 安装器只检查 HTTP 200，不校验 `/healthz` 的版本，也不检查端口归属；旧进程返回 200 会让安装器误报成功。
3. **DNS 修复未闭环**：`final` 只使用一个 DNS 服务器，0.1.10 的 `local2` 是死配置；UDP 53 仍可被污染；`CONFIG_POLICY_VERSION` 仍为 2；客户端和 Clash 模板仍有 `223.5.5.5`。
4. **在线状态不真实**：在线是“最近 60 秒有流量”，不是 TCP 连接；Users 页面不轮询；速率在无流量或采集中断后不归零。
5. **核心故障会黑洞整机**：系统代理开启时核心崩溃，运行期没有 fail-open，流量会一直指向已停止的本地端口。
6. **诊断名不副实**：doctor 只有数据库、核心、引擎、系统代理、TUN、证书；没有 DNS、端口归属、代理出口/TLS、版本一致性、配置漂移。
7. **安装/发布门禁偏弱**：测试大量是源码字符串断言；没有 frozen 版本测试、旧进程占端口测试、Windows 安装器实跑、DNS/在线/代理故障行为测试。

0.1.11 的目标是让以下五句话成立：

- 任一版本界面、CLI、安装器、核心 API 报告的是同一个可比较的版本事实。
- 安装器只有在“实际监听进程 + 控制面版本 + 核心版本”都匹配时才报告成功。
- 服务端默认使用加密 DNS，UDP 只是显式回退；不再存在不会生效的 DNS 配置。
- 一次诊断能区分 DNS、TCP、TLS、端口、版本、系统代理和配置漂移问题。
- 在线/速率语义诚实；核心故障不会让整机流量进入黑洞。

## 1. 目标与非目标

### 1.1 目标

1. **版本事实单一**：构建、安装、运行、核心、Web 五个版本面可比较，不一致时 UI/CLI/安装器明确报错。
2. **安装结果可证明**：端口归属、期望版本、核心运行状态、健康检查全部纳入安装/升级门禁。
3. **DNS 可信且可回退**：DoH 优先，UDP 显式回退；删除死配置；策略版本升级；客户端与订阅模板同步清理。
4. **诊断可定位**：doctor 能直接回答“DNS 错、TCP 错、TLS 错、端口被占、版本不对、配置漂移、代理状态不一致”。
5. **状态语义诚实**：在线/速率/最后流量/采集器状态明确；前端不再用旧数据伪装实时。
6. **故障可恢复**：核心崩溃时系统代理按策略 fail-open 或明确告警；显式 Disconnect 不被自动重连覆盖。
7. **门禁可信**：精确版本、安装器行为、DNS 行为、在线边界、代理故障进入自动化门禁；不再用 grep 代替执行。

### 1.2 非目标

- 新协议（NaiveProxy、TUIC、AnyTLS 等）、RBAC、多节点编排、计费/商业化、SSO。
- 数据库 schema 变更；0.1.11 不引入 Alembic 迁移。
- UI 全面重设计、设计系统换代、移动端原生 App。
- 修改上游 sing-box 源码以暴露 Clash API 用户元数据；该改动涉及定制核心、上游补丁和许可证声明，放到 0.2.0 评估。
- 独立 kill switch；项目当前明确不提供，0.1.11 不改这个边界。
- 静默自动更新；继续坚持“检查可以自动，安装必须显式”。
- 在没有实机证据时声称 Windows 11、macOS 14、Debian/RHEL、Nginx、Docker、ACME、TUN、72 小时 soak、性能或签名已经验证。

### 1.3 “全部都要做”的范围定义

本方案把上一轮列出的 **P0 与 P1 全部纳入 0.1.11**。P2 分为两类：

- 可在 0.1.11 内完成的代码/测试/文档项：纳入对应 P1 工作包。
- 需要上游核心改动、外部硬件、0.2.0 架构或明确非目标的项：记录在 §3.3，不伪装成 0.1.11 交付。

## 2. 证据基线

### 2.1 服务器现状（只读核对）

| 检查 | 结果 |
|---|---|
| 服务器版本 | `Ostium 0.1.10` |
| `/healthz` | `{"status":"ok","version":"0.1.10"}` |
| `runtime/last-good.json` DNS | `8.8.8.8` + `1.1.1.1`，`strategy: ipv4_only`，`final: local` |
| `runtime/last-good.meta.json` | `policy_version: 2` |
| 服务器直连 Google | HTTP 200，约 0.15s |
| 服务器直连 Hugging Face | HTTP 200，约 0.81s |
| Clash API `/dns/query` | Google 返回正确 A 记录 |
| 核心进程 | `/var/lib/ostium/core/sing-box run -c /var/lib/ostium/runtime/last-good.json` |

结论：0.1.10 的服务端 DNS 修复已经生效；当前不应再把“服务器 DNS 污染”作为客户端失败的默认解释。

### 2.2 UDP 53 仍不可信

在开发环境对同一域名做对比：

- `dig @8.8.8.8 www.google.com A` → `104.244.42.197`（错误 IP）
- `dig @1.1.1.1 www.google.com A` → `104.244.42.197`（错误 IP）
- DoH `https://1.1.1.1/dns-query` → `142.251.152.119` 等正确 A 记录

结论：UDP 53 可以被中间网络污染；0.1.10 的 UDP 方案只是“当前服务器可用”，不是长期可信方案。0.1.11 必须提供加密 DNS 优先路径。

### 2.3 `local2` 不会生效

sing-box 官方文档明确：`dns.final` 只指定一个默认 DNS 服务器，不会在服务器之间自动故障转移。0.1.10 生成：

```json
"servers": [
  {"type": "udp", "tag": "local",  "server": "8.8.8.8"},
  {"type": "udp", "tag": "local2", "server": "1.1.1.1"}
],
"final": "local"
```

`local2` 没有被任何 DNS rule 引用，因此不会参与解析。它不是冗余，而是死配置。

### 2.4 0.1.9 冻结产物版本正确

对已发布的 `Ostium-0.1.9-linux-amd64.AppImage` 做 `--appimage-extract` 后运行：

```text
Ostium 0.1.9
Python 3.13.13 ...
```

内部 `ostium_ctl-0.1.9.dist-info/METADATA` 的 `Version: 0.1.9`。这说明打包链路本身可以在冻结产物中带正确版本；Windows 页面显示 0.1.7 更可能是旧进程、旧安装、旧安装包或安装器误判，而不是“所有 frozen 包都读错元数据”。0.1.11 的版本契约会把这个判断变成确定事实。

## 4. 工作包详细设计

### WP1 版本契约与构建溯源（P0-01）

#### 目标

把“版本”从运行时偶然值变成构建时确定、运行时可比对的事实。

#### 新增/修改

- 新增 `src/ostium/build_info.py`：
  - `BuildInfo` 数据类：`version`、`commit`、`built_at`、`frozen`、`executable`、`argv`、`pid`、`process_started_at`、`python`、`prefix`、`package_path`、`dist_info_path`。
  - 版本解析顺序：
    1. `OSTIUM_BUILD_VERSION` 环境变量；
    2. `ostium._version.__version__`（构建生成）；
    3. `importlib.metadata.version("ostium-ctl")`；
    4. 最后才使用源码 fallback。
  - 冻结模式（`sys.frozen`）优先使用 `_version.py`，不依赖 `dist-info` 是否存在。
  - `commit` 来自 `OSTIUM_BUILD_COMMIT`，未注入时返回 `None`，不伪造。
  - `web_build` 从 `web/dist/build.json` 读取（见下），包含 `version`、`commit`、`digest`、`built_at`。
- `src/ostium/__init__.py` 改为从 `build_info` 读取 `__version__`、`USER_AGENT`；保留导入兼容。
- `src/ostium/api/routes_system.py` 新增 `GET /api/v1/system/provenance`（管理员）：
  - `app`：版本、commit、built_at、frozen、executable、pid、process_started_at、python、prefix、package_path、dist_info_path。
  - `web`：dist 路径、`build.json` 版本、PWA digest、index.html mtime/sha256。
  - `core`：running、pid、版本、engine_version、revision、config_sha256、last_error。
  - `listener`：host、port、PID、exe、start_time（psutil）。
  - `consistency`：`ok`/`mismatch`、`expected_version`、`mismatches[]`。
- `src/ostium/api/app.py`：
  - `/healthz` 返回 `status`、`version`、`commit`、`started_at`。
  - `/healthz`、`/readyz`、`/auth/status`、`/system/info`、`/system/provenance` 设置 `Cache-Control: no-store`。
  - `index.html`、`sw.js` 响应设置 `no-store`；hashed assets 保持 immutable。
- `src/ostium/cli/main.py`：
  - `ostium version --json` 输出 `BuildInfo`。
  - `ostium doctor` 增加 `version_consistency` 与 `port_owner`。
  - `ostium diagnostics export` 写入 `provenance.json`。
- 前端：
  - `web/src/api/types.ts` 增加 `Provenance`/`BuildInfo` 类型。
  - `web/src/api/index.ts` 增加 `api.system.provenance()`。
  - `web/src/pages/SettingsPage.vue` 增加 About/Build 卡片：版本、commit、构建时间、控制面 PID、核心版本、Web build、监听端口 owner；不一致时红色警告。
  - `web/src/pages/LoginPage.vue`：mount 时 `auth.bootstrap(true)`；版本未知显示 `unknown`，不显示旧缓存。
  - `web/src/stores/auth.ts`：logout 时清空 `version` 或标记 `version_unknown=true`。
  - `web/src/composables/useStatus.ts`：请求序号，旧响应不得覆盖新版本。
  - `web/src/layouts/AppLayout.vue`：页脚版本点击可打开 About/Provenance。
- 构建：
  - `web/vite.config.ts` 读取 `../VERSION`，注入 `__APP_VERSION__`、`__BUILD_COMMIT__`、`__BUILD_TIME__`。
  - `web/pwa.ts` 生成 `build.json`（版本、commit、digest、built_at），随 `web/dist` 打包。
  - `deploy/pyinstaller/ostium.spec` / `ostium-service.spec` 显式收集 `_version.py` 与 `build_info.py`。
  - `scripts/build-windows.ps1`、`scripts/build-linux-packages.sh`、`scripts/build-macos.sh`、`Dockerfile` 注入 `OSTIUM_BUILD_COMMIT`（有 `GITHUB_SHA` 时）。

#### 验收

- 在 wheel、PyInstaller 目录、Windows setup、Docker 镜像中分别运行 `ostium version --json`，`version` 精确等于 `VERSION`。
- `/healthz`、`/auth/status`、`/system/info`、`/system/provenance`、核心 `/v1/health` 的版本一致。
- 用旧进程占 8787 时，`/system/provenance.listener` 显示旧进程 PID/路径/启动时间，`consistency=mismatch`。
- 版本相关响应不被浏览器/反代缓存。
- 单测覆盖：metadata 缺失、frozen、版本不一致、Web build 缺失、旧响应竞态。

### WP2 安装契约：端口归属 + 版本断言（P0-02）

#### 目标

安装器只有在“实际监听进程、控制面版本、核心状态”都正确时才报告成功。

#### Windows

`deploy/windows/install.ps1`：

- 新增参数 `-ExpectedVersion`（默认从安装目录 `VERSION` 文件读取）。
- 从现有 `$DataDir\config.toml` 解析 `port`，默认 8787；不再硬编码健康检查端口。
- 新增 `Get-PortOwner($port)`：
  - `Get-NetTCPConnection -State Listen -LocalPort $port`；
  - `Get-Process -Id` 获取 `Path`、`StartTime`；
  - 返回 PID/路径/启动时间/版本（若可读取）。
- 安装前 `Stop-PreviousOstium($port)`：
  - 如果 owner 路径在 `$InstallDir`、`$env:ProgramFiles\Ostium`、`$env:ProgramData\Ostium` 或 owner 镜像名是 `ostium.exe`/`python.exe`/`ostium-service.exe`，停止并记录；
  - 未知进程不盲杀，抛出明确错误，附 PID/路径和 `Get-NetTCPConnection` 输出。
- 健康检查：

### WP3 DNS 解析器 v2（P0-03）

#### 目标

默认使用加密 DNS，UDP 只是显式回退；配置中不再有不会生效的服务器；策略版本与 DNS 变更绑定。

#### 配置

```toml
server_dns_mode = "auto"          # auto | doh | udp
server_dns_doh_url = "https://1.1.1.1/dns-query"
```

- 环境变量：`OSTIUM_SERVER_DNS_MODE`、`OSTIUM_SERVER_DNS_DOH_URL`。
- 默认 `auto`；服务端 TOML 保存；客户端忽略。
- `Settings.save()` / `load()` / `env_map` 同步。

#### 配置生成

`src/ostium/engine/singbox/config.py`：

- 新增 `ServerDnsSpec`（`mode`、`doh_url`、`server_tag`、`server_type`、`server`、`path`、`tls_server_name`）。
- `build_server_config` 只生成一个实际使用的 DNS server：
  - DoH：
    ```json

      "tag": "local",
    ```


新增 `src/ostium/engine/dns.py`（或 `services/dns_health.py`）：

- `probe_doh(url, timeout=5)`：用 `httpx.AsyncClient(trust_env=False)` 请求 DoH JSON API，查询 `www.google.com A`；返回是否成功、耗时、答案。
- `select_server_dns(settings)`：
  - `mode=doh`：只探测 DoH，失败则启动失败并提示改为 `udp`；
  - `mode=udp`：直接 UDP；
  - `mode=auto`：先探测 DoH，成功用 DoH；失败用 UDP，并写 warning/alert。
- 结果缓存 10 分钟；后台任务每 5 分钟复检；模式变化时 `reconcile_server(force=True)`。
- 探测不应阻塞启动：在 lifespan 中 `asyncio.to_thread` 或后台任务执行；首次 apply 前完成一次短探测。

#### `last-good.meta.json`

### WP6 系统代理 fail-open（P0-06）

#### 目标

核心崩溃时不让整机流量指向死端口；显式 Disconnect 不被自动恢复。

#### 配置

`src/ostium/config.py`：

```toml
system_proxy_fail_open = true
system_proxy_fail_open_seconds = 45
```

- 环境变量：`OSTIUM_SYSTEM_PROXY_FAIL_OPEN`、`OSTIUM_SYSTEM_PROXY_FAIL_OPEN_SECONDS`。
- 客户端 TOML 保存；服务端忽略。
- 默认 `true`：核心不可达超过 45 秒，关闭系统代理并告警；恢复后自动重新启用。
- 关闭：保持代理，但 UI 显示“这不是 kill switch，可能整机断网”。

#### 运行期

`src/ostium/api/app.py` 新增 `_proxy_watchdog`：

状态：

- `proxy_fail_open_since: float | None`
- `proxy_fail_open_active: bool`
- `proxy_restore_pending: bool`

逻辑：

1. 只在客户端、`mode=system_proxy`、`proxy.status().enabled` 时运行。
2. 核心不可达或 `running=false`：
   - 启动计时；
   - 先尝试 `reconcile_client(force=True)`；
   - 超过 `system_proxy_fail_open_seconds` 且配置开启：
     - `proxy.disable()`；
     - `bus.log("critical", ...)`；
     - `create_alert(level="critical", code="system_proxy_fail_open", ...)`；
     - 标记 `proxy_restore_pending=true`。
3. 核心恢复且 `client_paused=false` 且 `mode=system_proxy`：
   - 如果 `proxy_restore_pending`，重新 `proxy.enable()`；
   - 清除 alert/状态。
4. 显式 Disconnect：
   - `client_paused=true`；
   - watchdog 不恢复代理、不重启核心。
5. 正常关闭：
   - `proxy.disable()` 保持现有行为。

`src/ostium/system/proxy.py`：

- 增加 `is_owned(host, port)`：state 文件或平台状态指向本机 mixed_port。
- 增加 `disable_if_owned()`：只恢复自己拥有的代理，不破坏用户手工配置。
- `recover_if_stale()` 保留启动恢复；增加“state 丢失但平台代理指向我们端口”的识别（Windows 注册表、macOS networksetup、GNOME/KDE）。
- Windows `uninstall.ps1` 使用 `disable_if_owned` 语义。

#### UI

- Settings → Network 增加 “Core failure proxy policy”：
  - 默认 “Restore direct internet (recommended)”；
  - 可选 “Keep proxy (may blackhole traffic)”；
  - 说明无 kill switch。
- Network 页面显示 `proxy_fail_open` 状态与上次触发时间。
- Dashboard 显示 critical alert。

#### 测试

- 模拟核心不可达 44/45/46 秒，断言代理在阈值后关闭；
- 核心恢复后代理重新启用；
- `client_paused=true` 时不恢复；
- `system_proxy_fail_open=false` 时只告警不关闭；
- Windows 注册表 state 丢失但指向我们端口 → 卸载/恢复能识别；
- 正常关闭写 `clean_shutdown=true`。

#### 验收

- 杀核心后 45 秒内系统代理关闭，产生 critical alert；
- 核心恢复后代理自动恢复（未显式 Disconnect）；
- 显式 Disconnect 后不自动恢复；
- 不破坏用户手工配置的代理。

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| DoH 被网络封锁 | 服务器无法解析 | `auto` 探测 + UDP 回退 + doctor/alert；允许 `server_dns_mode=udp` 显式配置 |
| DoH 配置 `detour: direct` 导致核心 FATAL | 核心起不来 | 省略 `detour`；`sing-box check` + 实际 `run` 测试；文档记录 |
| policy 3 升级瞬间核心等待 | 短暂无代理 | 安装器等待核心 `running:true`；升级文档说明；回滚路径明确 |
| fail-open 导致直连泄漏 | 流量短暂不走 VPN | 默认开启但 UI 明确提示“无 kill switch”；允许关闭；critical alert |
| 在线仍不是精确设备数 | 用户误解 | 改名“近期活跃”；tooltip/文档；P2 记录定制核心方案 |
| 端口 owner 检测误杀 | 破坏用户进程 | 只停止已知 Ostium 路径/镜像；未知进程拒绝并提示 |
| Windows 自定义端口 | 健康检查错误 | 从 config.toml 读取端口；测试覆盖 |
| 版本注入不完整 | 仍有 unknown | 构建脚本统一注入；preflight 检查 `build.json`；artifact inspection |
| 范围过大 | 延迟发布 | P0/P1 分批提交；P2 明确 defer；每批独立测试/回滚 |
| 诊断包泄露 | 敏感信息外泄 | 统一 redaction；测试覆盖；只允许管理员下载 |
