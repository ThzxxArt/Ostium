# Ostium v0.1.2 decisions

These decisions were made while implementing the 0.1.2 plan. They are scoped to
this release and do not change the 0.1.1 published artifacts.

## D-101 Fail-closed enforcement state

The control plane writes disabled-user names to `data_dir/enforcement.json`
before applying a quota/expiry change. The privileged core strips those users
from `last-good` on every start. This is intentionally redundant with the
database: it closes the window where the control plane committed a disable but
the core restarted from an older configuration.

## D-102 Configuration policy version

`last-good.meta.json` records `policy_version`. The core refuses to start a
server configuration produced by an older policy and waits for the control
plane. The control plane reconciles at startup and every 30 seconds. This is
stronger than “apply once at startup” and avoids silently running 0.1.0/0.1.1
egress rules after an upgrade.

## D-103 Backup format v2

Backup v2 is additive: it includes `rulesets/` and `acme/`, checksums every
member, and stores certificate/rule-set paths relative to `data_dir`. V1
backups remain importable. A database with encrypted fields is rejected if the
archive lacks `master.key`; generating a replacement key would silently make
the data unreadable.

## D-104 Public UI recovery console

If Public UI is enabled but no unexpired certificate or TOTP is available, the
CLI serves a plaintext recovery console only on `127.0.0.1`. It never falls back
to a public plaintext bind. Renewal writes `runtime/reload-ui`; the CLI rebuilds
the TLS listener without a service restart.

## D-105 Version source and installer default

`VERSION` is the single repository version source. Installers default to
`latest` instead of pinning the previous release. Release jobs pass the tag
version explicitly; `scripts/release-preflight.sh` checks all live version
strings and refuses a dirty tree unless `--skip-git` is used for a dry run.

## D-106 Draft-first publication

The release workflow creates a draft GitHub Release with all assets, verifies
the checksum manifest and the asset/platform set, publishes PyPI, then promotes
the verified GHCR staging digest and makes the draft public. A failure before
PyPI leaves only a draft and staging tags.

## D-107 DNS pinning without replacing httpx

The fetcher resolves and validates every address, then temporarily pins
`socket.getaddrinfo` for that hostname during the HTTP request. TLS SNI and the
Host header stay correct, existing httpx/respx tests keep working, and a second
DNS answer cannot redirect the connection to metadata. Requests are serialized
with a lock so two hosts cannot observe each other's pin.

## D-108 API token scopes

Legacy `read`/`write` scopes remain valid. Sensitive reads now accept narrower
scopes (`subscription:read`, `user:read`, `backup:read`) and `write` retains
full access. Cookie sessions and the loopback CLI token are unrestricted.

## D-109 TOTP replay semantics

A successful login consumes the TOTP code for 180 seconds. TOTP setup
confirmation uses `consume=False` so the same code can be used immediately for
the first login; subsequent logins require a new code.

## D-110 Platform claims

Windows/macOS/Debian/RHEL/Nginx/Docker/ACME/TUN/soak/performance/signing are not
claimed as verified unless executed on the relevant environment. The release
status page is the maintained list; unexecuted items stay blockers.

## D-111 Publication-ordering residual (P0-07) — accepted

The release owner accepts the implemented PyPI-first order: a draft release with
all assets and checksums is created and verified first, then PyPI is published,
then the verified GHCR digest is promoted and the draft is made public. This is
not atomic. If GHCR promotion or draft publication fails after PyPI, the draft
is kept for retry; if it cannot be completed, the PyPI version is yanked and the
fix ships as a patch. PyPI is the first irreversible public step and is treated
as such in `docs/release-status.md` and the release checklist.

## D-112 Service-isolation waiver — accepted for 0.1.2

The control plane and the core continue to run as the same `ostium` user on
Linux. Full service-user/capability separation is a 0.2.0 architecture item and
is **not** claimed as fixed. Compensating controls remain: the core API binds
loopback only, validates a role-separated configuration whitelist, and the
packaged units apply filesystem/privilege hardening.

## D-113 Unit-only coverage waiver — accepted with follow-up

The release gate remains the repository/package coverage gate, which passes at
94.19% statements / 90.52% branches. The separate 75/65 target for
`tests/unit` in isolation is deferred: the current mix relies on in-process API
tests that exercise real database transactions. A follow-up is recorded to add
unit-only coverage for CLI, supervisor and backup branches. This waiver does
**not** claim the unit-only target is met.

## D-114 Platform tiers and signing

- Tier 1 (release-gated locally): Linux x86_64/arm64 — wheel/sdist, installer,
  DEB, AppImage, Docker image.
- Tier 2 (published, runtime evidence outstanding): Windows x86_64 and macOS
  arm64. Their assets are labelled **unsigned** unless the release owner
  supplies Authenticode / Developer ID credentials and creates the protected
  `release-signing` environment.

No Windows/macOS/ACME/Nginx/Docker/TUN/soak/performance evidence is claimed
until it is actually executed.

## D-115 Release authorization

Local review, fixes, tests and commits are complete. Pushing the branch,
creating the `v0.1.2` tag, and publishing PyPI/GHCR/GitHub Release require the
release owner's explicit confirmation. No agent may decide this on its own.
