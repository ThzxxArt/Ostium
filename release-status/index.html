    This page is the single source of truth for what is published, what was verified, and what remains an accepted blocker. Version-specific notes live in CHANGELOG.md and RELEASE_NOTES.md; this page records the delivery facts.

    0.1.10 verification status¶

    Verified locally¶

    • Backend unit and in-process integration tests: 713 passed / 10 deselected; 94.33% statements / 90.49% branches; coverage_gate.py passes.
    • Real sing-box integration tests with the pinned 1.14.4-ostium.1 core: 10 passed.
    • Frontend typecheck, lint, unit tests, production build and formatting: 204 passed; 90.86/85.90/88.63/92.40.
    • TOTP regressions: the status endpoint advertises login_totp_required before login; six password-only attempts leave failed_attempts=0 and locked_until=NULL; a wrong TOTP still locks after five failures; a correct TOTP logs in after the password-only challenges.
    • Windows installer scripts parse with PowerShell 7.7; the generated ostium-ui.ps1 template parses too. The scheduled task uses a hidden PowerShell wrapper, waits for /healthz, writes ui.log, and updates the machine PATH.
    • 0.1.5 Windows failure reproduced as ModuleNotFoundError: No module named 'aiosqlite'; both PyInstaller specs now collect aiosqlite. A local PyInstaller build served /healthz after the spec fix.
    • The 0.1.5 service reproduced SCM error 1053. sc qc showed an image path with no arguments; the frozen entry point now calls Initialize, PrepareToHostSingle and StartServiceCtrlDispatcher itself when SCM starts it without arguments. Interactive debug/install/remove still use HandleCommandLine. Heavy imports run inside SvcDoRun after SERVICE_RUNNING.
    • Interactive Windows installs now show a visible PowerShell console with the service registration, Start-Service, 8787 health check and failure details; silent installs stay hidden and write install.log.
    • The 0.1.7 UI launcher failure was reproduced from ui.log: uvicorn started, PowerShell emitted NativeCommandError, and the wrapper exited with code 1. ostium-ui.ps1 now uses ErrorActionPreference=Continue, writes all output to ui.log, and checks the child exit code.
    • Windows installer keeps the UI installable when the service fails, writes install.log/service.log/service-bootstrap.log, stops orphan ostium-service/sing-box processes, and embeds the Ostium icon.
    • Generated Clash YAML was accepted by Mihomo 1.19.34 with mihomo -t; it contains fake-IP DNS, ipv6: false, and GEOIP,CN,DIRECT,no-resolve.
    • Server IPv4-only failure reproduced: curl -4 returned 200 for Google and Hugging Face, curl -6 failed, while IPv4-only GitHub worked. Generated server config now uses dns.strategy: ipv4_only and route.default_domain_resolver to the internal local server; sing-box check accepts it.
    • Server DNS pollution reproduced: 223.5.5.5 returned 104.244.42.197 for Google and 157.240.3.8 for Hugging Face, while system DNS returned correct A records. Generated config now uses 8.8.8.8 and 1.1.1.1, not 223.5.5.5.

    • 0.1.10 install/reinstall/uninstall e2e passed; reinstall kept exactly one administrator.

The wheel and sdist SHA-256 values match between the GitHub Release and PyPI.

    Signing status¶

    No Windows Authenticode or Apple Developer ID certificate is configured in this repository. Until the release owner supplies one, affected assets must be listed as unsigned in the release notes. Checksums and GitHub build provenance are not a substitute for platform code signing.

    The release workflow expects a protected GitHub environment named release-signing with required reviewers for the Windows/macOS jobs. Create and configure it (required reviewers, deployment branches) before tagging. GitHub creates a missing referenced environment automatically without protection rules, so the jobs would start unsigned rather than being blocked. The pypi environment must be protected the same way; a v* tag push must not be able to publish without release-owner approval (D-115).

    Release decisions (D-111～D-115)¶

    The release owner accepted the following in versions/V0.1.2_DECISIONS.md; the RC evidence is in versions/V0.1.2_RC_REPORT.md:

    • D-111 PyPI-first ordering is accepted with the documented retry/yank/patch recovery; publication is not atomic.
    • D-112 Control-plane/core service isolation remains a 0.2.0 item.
    • D-113 The unit-only 75/65 coverage target is deferred; the repository and package gate at 94.29/90.44 is the release gate.
    • D-114 Linux is Tier 1; Windows/macOS are Tier 2 and published unsigned unless signing credentials are supplied.
    • D-115 Push, tag and publication require explicit release-owner approval.

    Release gates for 0.1.10¶

    1. Code and automation: ruff, mypy, shellcheck, mkdocs strict, backend and frontend suites, real-core integration, coverage gates.
    2. Upgrade and data: 0.1.9 -> 0.1.10 upgrade plus backup restore; missing-key and corruption rejection. The installer's staged rollback files and the database snapshot are the recovery path if health checks fail.
    3. Platform evidence: record only what was actually executed; unexecuted items stay blockers.
    4. Publication ordering: draft release verified first, PyPI published only after that verification, then GHCR version/latest tags promoted and the draft made public. PyPI is the first irreversible public step; a later failure keeps the draft for retry and requires a yank/patch if it cannot be completed.

    Rollback¶

    • Before publication: delete the draft release and local tag; published versions are untouched.
    • After PyPI succeeds but the draft cannot be published: keep the draft, fix the publication step, or yank the PyPI version and publish a patch.
    • Installation failure: restore the previous virtualenv and the database snapshot; the installer keeps its staged/venv rollback files for diagnosis.
    • Restore failure: the staged backup is kept for retry and the previous database is restored before an error is returned.
